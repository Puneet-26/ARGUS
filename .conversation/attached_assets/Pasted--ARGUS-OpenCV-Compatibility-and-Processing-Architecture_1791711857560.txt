# ARGUS: OpenCV Compatibility and Processing Architecture

## 1. Core Requirement

ARGUS is an educational computer vision investigation platform for a two-day OpenCV workshop.

The application must teach participants how image-processing algorithms work through direct experimentation. Every investigation stage must connect a visual result to the underlying OpenCV operation.

The frontend is a React + TypeScript web application. The computer vision engine must use Python and OpenCV wherever actual OpenCV functionality is required.

**Do not replace OpenCV with CSS filters, decorative overlays, hardcoded outputs, or simulated algorithms while claiming they are genuine OpenCV processing.**

## 2. Architecture

Use this architecture:

React + TypeScript frontend
→ Python FastAPI backend
→ OpenCV processing pipeline
→ Processed image or structured result
→ Frontend evidence viewer

Use FastAPI for communication between the browser and Python. Keep processing functions modular so that individual algorithms can be tested independently.

Recommended dependencies:
- Python 3.11 or another version supported by the selected OpenCV and project dependencies.
- `opencv-python`
- `numpy`
- `fastapi`
- `uvicorn`
- `python-multipart` for multipart file uploads when required.

Choose mutually compatible package versions and document installation commands.

Do not install `opencv-python-headless` alongside `opencv-python` in the same environment. For a server deployment without GUI dependencies, use the headless package instead.

Never use `cv2.imshow()` or other desktop GUI functions in the web backend. Return processed images to the browser.

## 3. Level 1: Eyes Online

Teach foundational image processing through a real corrupted CCTV image.

Implement actual OpenCV operations:

- Load and validate image input using `cv2.imdecode()` or `cv2.imread()`.
- Inspect image dimensions and channels.
- Convert BGR to grayscale with `cv2.cvtColor()`.
- Adjust brightness and contrast using pixel operations or `cv2.convertScaleAbs()`.
- Apply histogram equalisation using `cv2.equalizeHist()`.
- Apply CLAHE using `cv2.createCLAHE()`.
- Apply Gaussian blur using `cv2.GaussianBlur()`.
- Apply binary thresholding using `cv2.threshold()`.
- Apply adaptive thresholding using `cv2.adaptiveThreshold()`.
- Crop and resize using NumPy slicing and `cv2.resize()`.

The interface must show:
- Original image.
- Processed image.
- Before-and-after comparison.
- Adjustable algorithm parameters.
- Processing history.
- Current operation and relevant parameter values.
- A reset action.
- A way to save a finding into the evidence notebook.

Each operation must produce a real processed image from the supplied source. The intended timestamp clue is 23:42, but the application must not reveal it before the participant performs the relevant analysis.

Do not guarantee that CLAHE or thresholding will recover information absent from the source image. The supplied evidence asset must actually contain enough visual information to support the exercise.

## 4. Level 2: The Missing Clue

Teach object detection and scene comparison.

Use two clearly labelled modes:

**Mode A: OpenCV scene comparison**
- Image alignment where appropriate.
- Grayscale conversion.
- Absolute frame difference using `cv2.absdiff()`.
- Thresholding and contour extraction.
- Visualisation of changed regions.

**Mode B: YOLO object detection**
- Integrate a real, configurable YOLO model only if its dependencies and weights are available.
- Run inference on the selected evidence image.
- Return bounding boxes, class labels, and confidence values.
- Draw detection overlays on a copy of the original image.
- Clearly distinguish detector predictions from confirmed facts.

If YOLO weights are unavailable, the scene-comparison exercise must still work. Do not invent detections or claim that YOLO ran when it did not.

## 5. Level 3: The Red Bag

Teach colour spaces, thresholding, segmentation, and contours.

Implement:
- BGR-to-HSV conversion using `cv2.cvtColor()`.
- Adjustable lower and upper HSV thresholds.
- Binary colour mask using `cv2.inRange()`.
- Optional morphological opening and closing using `cv2.morphologyEx()`.
- Contour extraction using `cv2.findContours()`.
- Bounding rectangles using `cv2.boundingRect()`.
- An overlay displaying the segmented candidate regions.

Show the original image, mask, and segmented result together.

Changing the HSV controls must immediately or on explicit Apply produce a new real processing result.

Do not identify the owner of the bag from colour segmentation. Colour detection identifies candidate pixels or objects, not a person's identity or ownership.

## 6. Level 4: Follow the Trail

Teach video frames, motion analysis, and object tracking.

Implement:
- Video input using `cv2.VideoCapture()` on the backend.
- Frame-by-frame playback through API requests or a suitable streaming mechanism.
- Frame navigation and timestamp display.
- Frame differencing using `cv2.absdiff()`.
- Motion thresholding.
- Contour-based movement candidates.
- Centroid calculation for selected moving regions.
- Entry/exit-line crossing based on tracked positions.
- A chronological event log.

For reliable workshop operation, include a prepared frame-sequence fallback if live video processing is unavailable.

Do not claim to identify a person from a moving blob or red-colour candidate. Keep visual algorithm outputs separate from fictional witness statements and prepared system logs.

## 7. API Design

Create modular endpoints such as:

- `GET /api/health`: report backend and OpenCV availability.
- `POST /api/image/process`: apply a selected image-processing operation.
- `POST /api/image/compare`: compare two evidence images.
- `POST /api/detection/yolo`: run YOLO when configured.
- `POST /api/colour/segment`: generate an HSV mask and segmented image.
- `POST /api/video/frame`: retrieve or process a selected video frame.
- `POST /api/video/analyze`: analyse a prepared video or frame sequence.

Validate uploaded file type, file size, image dimensions, operation names, and numerical parameters. Handle malformed images, missing assets, unavailable models, and failed video decoding with useful error messages.

Return structured JSON containing operation metadata, parameter values, and result URLs or encoded image data. Avoid sending unnecessarily large images as base64 JSON when a more efficient response is practical.

Keep uploads temporary unless the user explicitly saves evidence.

## 8. Evidence Integrity

Every result must indicate its origin:
- Actual OpenCV processing.
- Actual model inference.
- Prepared workshop asset.
- Fictional narrative record.

Keep these categories distinct in the interface.

The evidence notebook should record the operation used, relevant parameters, source asset, and resulting observation when appropriate.

A detected region is not automatically proof of identity, ownership, intent, or guilt.

## 9. Deployment and Compatibility

The browser frontend and Python backend are separate processes.

For local development:
- Run the frontend with Vite.
- Run the backend with Uvicorn.
- Configure a development proxy or explicit API base URL.
- Handle CORS correctly when separate origins are used.
- Include clear setup and startup instructions.

For hosted deployment, select a hosting environment that supports a Python backend and its native dependencies. Do not assume a static frontend host can execute Python OpenCV code.

Avoid unnecessary GPU requirements. The initial implementation should work on CPU using small prepared images and short video clips.

Add a backend health indicator to the interface so participants can tell whether actual processing is available.

## 10. Acceptance Tests

Before declaring OpenCV integration complete, verify that:

1. The backend starts and reports its OpenCV version.
2. A valid image can be uploaded and decoded.
3. Grayscale conversion returns a genuinely grayscale result.
4. Brightness, contrast, CLAHE, and thresholding return different results when parameters change.
5. HSV segmentation returns a binary mask and a segmented image.
6. Scene comparison identifies changes between supplied images.
7. Invalid images and invalid parameters return meaningful errors.
8. The frontend displays returned processing results rather than pretending to process images locally.
9. Evidence can be recorded and persists across page reloads.
10. Optional YOLO and video features report unavailable dependencies honestly instead of crashing the application.

Implement and test Level 1 end to end before expanding the remaining levels. Preserve the existing visual design requirements: dark charcoal surfaces, muted red and amber accents, condensed typography, and absolutely no green backgrounds.
